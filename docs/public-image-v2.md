## Correct contract and local evidence

`portal.js:132-135` generates a random object name, uploads it, then inserts a photo row without an ID. `202609120001_inventory.sql` gives that row a separate `gen_random_uuid()` default. Uploads therefore use `<vehicle UUID>/<object UUID>.webp`; the object UUID need not equal the photo row ID. The v1 equality check incorrectly rejected legitimate uploads.

`202609180001_drive_photos.sql` uses a different contract for Drive: `<vehicle UUID>/<photo row UUID>.drive`, backed by a private `vehicle_drive_photos` row. The existing SQL migrations are exercised in a fresh in-memory PGlite database: an upload inserted without a row ID gets an independent ID, remains visible through existing anonymous RLS when published, and loses anonymous object access when withdrawn. This verifies checked-in schema behavior; it is not a claim that a live migration was inspected or applied.

The v2 upload route uses the exact path on the selected associated photo, validates a canonical vehicle namespace and UUID WebP basename, and downloads through the anonymous client from the fixed existing `vehicle-photos` bucket. It accepts no caller-supplied file, folder, path or ticket. It rejects encoded traversal, arbitrary URLs, extra path components, unsupported source/type, empty and oversized bodies. Uploads do not require Drive credentials.

Drive requests first prove the published public vehicle and photo association through anonymous RLS. Only then does the existing server client read the matching private link, constrained by both vehicle and photo IDs. The folder must be the saved folder under the configured root and match the vehicle's full plate; file ID, folder parent, download capability, checksum, type and byte count must match. The existing adapter checks actual bytes and checksum and enforces 20 MiB. No arbitrary Drive file or folder selector is exposed.

Both branches re-read the current first photo and publication after awaited reads. Drive also compares the entire private association, including file/folder/checksum/MIME/size. A withdrawn/reassigned/removed/replaced/reordered relation discards fetched bytes. These are before/after access checks, not a transaction spanning a remote download: a change after the final check can race the response, and already delivered bytes cannot be revoked. `no-store` avoids intentional browser/CDN caching.

Public responses contain only the image or a fixed error. Upstream error messages, internal IDs, credentials and signed URLs are not returned or logged. Caller Authorization/cookies do not enter the public database/storage client. Legacy signed-ticket GET and POST implementations remain unchanged from the base commit; their regression suite still runs.
