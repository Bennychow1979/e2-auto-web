Implemented
- New dispatch creates a simulated Telegram message with job details and a link.
- Viewing a message is not acceptance. Only the assigned active Runner can confirm.
- Acceptance stores a server timestamp and audit event; duplicate retries do not
  create another acceptance. Vehicles cannot start movement before acceptance.
- Saving edits or reassigning a job clears acceptance, increments the dispatch
  version and starts a fresh confirmation/reminder period.
- At 15 minutes without acceptance, one simulated Admin reminder per dispatch.
  Acceptance or cancellation resolves the active warning. Historical records remain.
- Admin can use Simulate +15 minutes; Runner cannot access this control or RPC.
- Runner cannot read another Runner's job link or notification.
- Includes previous Carro collection, invoice-delivery jobs, shared From/To saved
  locations, and Inspector draft/submitted/returned summary cards.

Implementation boundary
- Acceptance is implemented in the unpublished runner/bills SQL migration and is
  exercised with the local SQL engine and authenticated-role policies.
- Telegram transport, Bot creation, verified employee chat binding, production
  scheduled worker, delivery failures/retries and real background delivery are NOT
  connected. No Telegram credential was read or requested. No external messages.
- Notification storage and the virtual clock exist only in the local preview
  server. Timeout evaluation runs when the preview is read (the open page refreshes
  every 15 seconds); this is NOT a deployed background reminder scheduler.
- Preview role selection is synthetic, only injected by the local test server.
  It must never be used as production authentication or Telegram account binding.
- Before any release, implement and verify real Bot/employee binding, private
  server-side transport, durable notification outbox, timer worker, recipient
  configuration and retry/cancellation checks. User approval is still required.
